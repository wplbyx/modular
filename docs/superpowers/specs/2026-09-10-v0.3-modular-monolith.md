# modular v0.3 Modular Monolith

## Product contract

modular is modular-monolith-first. A project starts with one Process hosting multiple Business Modules and may later extract selected modules. Extraction is checked and guided, not claimed to be transparent.

## Architecture model

- A Business Module owns business rules and data writes. Other modules import only its `contract` or generated protobuf package.
- A Process owns one Application, identity, logger, telemetry pipeline, health manager, event bus, and at most one HTTP and one gRPC server.
- Process identity comes from `Application.Name/Version/InstanceID/Metadata`; scaffold-once business wiring may return one optional Registrar while the default monolith leaves it nil.
- `.modular/architecture.yaml` is the user-maintained source for module dependencies, process assignment, process capabilities, and extraction blockers. It uses JSON-compatible YAML so the repository-local Python tool has no YAML runtime dependency.
- `.modular/manifest.json` remains generated-file replay and ownership state.
- Application remains a lifecycle orchestrator. Module construction stays in the typed composition root and does not use a runtime container.

## Synchronous contracts

Protobuf defines external and cross-module stable messages. `protoc-gen-go-modular` generates an unary `XxxServicePort` without `grpc.CallOption` and a Remote Adapter around the standard generated gRPC client. A local implementation satisfies the same Port directly. Streaming is not adapted to local calls automatically.

Local calls preserve `context.Context` cancellation and metadata but do not run transport interceptors or protobuf serialization. Requests are read-only and implementations must not retain them. Remote adapters normalize gRPC errors through `errs.FromError`.

## Consistency

Transactions stop at a Business Module by default. Each module defines the smallest UoW port required by its use cases; infrastructure adapters implement it for the selected database library. A necessary cross-module transaction is recorded as a `shared-transaction` Extraction Blocker.

The in-process EventBus remains a best-effort Local Notification mechanism. Durable Integration Events require an outbox/inbox adapter when an extraction creates a Process boundary.

## Lifecycle

Application runs Resource Setup in FIFO order, starts Endpoints in parallel, waits for explicit readiness where supported, and then registers the Service Node. Shutdown marks the process draining, unregisters it, stops Endpoints in parallel, and closes Resources in LIFO order. A zero-Endpoint Application is long-running and waits for context cancellation after Resource Setup.
