# modular v0.4 Pure Modular Monolith

## Product contract

modular scaffolds one deployable Go Application made of bounded-context
Business Modules. It does not model module extraction or transparent switching
between monolith and microservices. This self-contained module layout remains
the v0.4 product model; it is not a new architecture version.

`.modular/architecture.yaml` schema 2 contains one `application` with its name,
transports, ports, and shared resources, plus an acyclic `modules` dependency
map. It does not classify modules as CRUD/domain/consumer and does not record
project-specific migrations.

## Generated layout

```text
<project>/
  .modular/
    architecture.yaml
    manifest.json
    profile.toml
    tool/
  cmd/<application>/
    main.go
    resources.go
    modules.go
  config/<application>/
    config.go
    config.yaml
    locales/
      en.yaml
      zh-CN.yaml
  modules/<module>/
    bootstrap.go
    config.go
    contract/
      doc.go
    internal/
      service/doc.go
      app/doc.go
      api/doc.go
      domain/doc.go
    infrastructure/         # Agent-created adapters justified by use cases
  README.md
  go.mod
```

New projects have no root `internal`, centralized project infrastructure,
independent bootstrap package, generated `*.gen.go`, `.modular/make`, or
Makefile. `.modular/tool` remains a replayable local fallback; the CLI shipped
with the installed `$modular` skill is the standard command entrypoint.

## Module boundaries

A Business Module owns its behavior, use cases, public Go contract, adapters,
and data writes. Its root package exposes only the module Config and `New(...)`
constructor. The generated `func New()` is a neutral shell for a module that
has no dependencies or returned services; as contracts emerge, the Agent
replaces its signature with the real ports and service results. Constructor
parameters include sibling contract interfaces when the architecture declares
a dependency.

`contract` is the module's outward protocol: narrow hand-written Go interfaces,
Command/Query/Result values, and events deliberately shared with consumers.
Repository, publisher, external-client, and transaction ports are defined by
their consuming use cases in `internal/app`, not in `contract`.

The module-level `internal` directory is the compiler boundary. The same
module's `infrastructure` can import private ports and DTOs while `cmd` can
import the infrastructure package to construct it. Sibling modules may import
only `modules/<provider>/contract`, and every such import must correspond to an
edge in the architecture DAG. Importing a sibling root, `internal`,
`infrastructure`, ORM model, transport DTO, table, or transaction handle is
invalid.

The uniform shell is structural, not a demand for artificial behavior. A CRUD
module can leave `internal/domain/doc.go` explaining why no domain model exists;
an event-only module can leave `contract/doc.go` explaining why it has no
synchronous API. Complete-phase test checks ignore doc-only packages.

## Composition and data flow

Assembly has two levels. `cmd/<application>` is the outermost composition root;
`modules/<module>/bootstrap.go` is each module's local composition root. Detailed
interface design rules and an example live in
[layering](../../../agent/modular/references/layering.md).

Business contracts serve sibling modules; the module root's Config,
Dependencies, Module, and `New(cfg Config, deps Dependencies) (*Module, error)`
serve cmd. Assembly inputs/results must be usable without importing internal
types. Bootstrap constructs private adapters and use cases from narrow Providers
and sibling contracts, exposing only public capabilities and necessary hooks.
The empty generated constructor represents an assembly shell, not business
success. Existing scaffold-once constructors remain user-owned.

Application-level responsibilities:

- `main.go` creates the signal context and root config command, then constructs
  logging, catalog, policy, shared server, ServiceNode, and Application in
  lifecycle order.
- `resources.go` constructs library Resources, typed Providers, health checks,
  and a migration Resource. Projects do not wrap shared modular facilities in a
  second project-level infrastructure layer.
- `modules.go` defines stable `moduleAssembly` and
  `wireModules(resources sharedResources, cfg *Config)` seams. Its user region calls module
  `New(...)` in DAG order, connects their contracts, mounts routes/subscriptions, and returns
  checks and migration callbacks.

Module bootstrap connects objects without reading uninitialized Providers,
executing migrations, starting background tasks, or consuming messages. Cmd
collects lifecycle objects and callbacks for Application-managed execution.
Business sequencing, transaction decisions, and recovery remain in the initiating
use case. Contracts document success, error, and side-effect semantics, plus
concurrency and idempotency where relevant; behavior tests verify those promises.
Structural verification alone does not establish business correctness.

Database setup precedes the aggregate migration Resource. Module migrations
run through callbacks supplied by their persistence adapters; dependent
Resources and all Endpoints start only after migration succeeds. Resource close
remains LIFO. Repositories retain `core.Provider[T]` and do not call `Value()`
before Application Setup.

The Application owns one runtime identity, logger, health manager, transport
policy, resource set, EventBus, and at most one server per enabled protocol.
Modules register adapters on those shared facilities; they do not construct
parallel Application runtimes. EventBus is best-effort process-local delivery.
An external durability requirement needs an explicit Outbox/Inbox design.

## Config and errors

`config/<application>/config.go` aggregates `configitem.*` values and each
module's root Config and embeds `locales/*.yaml` for cmd. `config.yaml` follows
the same hierarchy. The generated locale catalog contains `en.yaml` and
`zh-CN.yaml`, defaults exactly to `en`, and initially defines at least
`UNKNOWN`; filenames must exactly represent their locale tag.

For GORM/SQLite, generated defaults enable WAL and a 5000ms busy timeout and set
`MaxOpenConn=1` and `MaxIdleConn=1`. This provides deterministic single-writer
behavior for the scaffold while remaining editable project configuration.

## CLI and ownership

The tool version for this layout is 4.1.0. `init` accepts an independent Go
module path:

```text
init shop --module-path github.com/example/shop --modular-version v0.4.0
```

Omitting `--module-path` retains the project-name default. `module add` creates
the uniform scaffold-once module shell. `resource add idgen --driver uuidv7`
adds the coordination-free ID Resource. Existing transport/resource/module/DAG
commands retain their v0.4 meaning.

Manifest schema 2 records `scaffold-once`, whole-file `managed` runtime assets,
and `region-managed` entries with each named region body hash. Go uses paired
`// modular:managed-begin|end <id>` markers. Sync changes an intact managed
region while preserving adjacent user content. A missing, duplicated, or
modified region is a transaction-wide conflict detected before any write.
Application `config.yaml` is refreshed only while its scaffold-once hash still
matches; after a user edits runtime values, later commands preserve the whole
file and require new defaults to be reconciled manually.

Module removal deletes only unchanged generated shell files. Modified or
untracked module content blocks the operation atomically. Destructive commands
preview by default and require `--apply`; `--dry-run` and `--diff` remain
available. The manifest and architecture update in the same transaction as
generated content.

## Verification

- `doctor --strict --phase framework|contract|complete` checks layout,
  ownership, placeholders, module imports, and the architecture DAG without
  mutation.
- `verify --phase framework` performs strict framework checks and
  `go build ./...`.
- `verify --phase contract` rejects unwired business, permits an explicit
  `modular:contract-unimplemented`, and runs `go build ./...`.
- `verify --phase complete` rejects all unfinished markers, requires tests for
  non-doc source packages matched by `.modular/profile.toml` (app/domain by
  default), then runs
  `gofmt -l`, `go build ./...`, `go vet ./...`, and
  `go test -race ./...`.
- `coverage` remains an independent report with no universal numeric threshold.

## Migration

`migrate v0.3-to-v0.4` still accepts only a v0.3 architecture with one Process.
It lifts that Process into `application`, removes extraction metadata, safely
moves module trees/config to the self-contained layout, rewrites exact Go import
paths, and removes recognized unchanged generated wiring/Buf scaffolds.
Moved non-Go files retain their exact bytes and file modes; legacy module-tree
symlinks stop for manual migration. A customized profile retains its content
while `internal/modules/` business-glob prefixes move to `modules/`.

Customized central wiring or policy, multiple Processes, modular protobuf
generator references, and `*_modular.pb.go` output stop automatic migration
with actionable errors. Explicit external proto/Buf assets remain user-owned.
The migration never guesses how to combine Processes or translate customized
composition code.

Projects already generated with the former centralized v0.4 layout receive an
explicit manual-migration error based on manifest layout. They are not silently
rewritten or overwritten.

## Acceptance scenario

`shop` is an illustrative forward-evaluation project, not the default `init`
business template. It uses `github.com/example/shop`, modular v0.4.0, HTTP,
GORM/SQLite, EventBus, and UUIDv7, with two routes:

- `customer`: CRUD-style `Reader` contract and
  `GET /api/v1/customers/{id}`; no domain types.
- `order`: domain aggregate, `Placer` contract, customer lookup, GORM adapter,
  `POST /api/v1/orders`, and post-commit `OrderPlaced` publication.
- `notification`: event consumer with no synchronous contract; its EventBus
  adapter maps `OrderPlaced` into a private Handler.

The DAG is `order -> customer` and `notification -> order`. Acceptance covers
the full target layout, both HTTP routes, migration ordering, event mapping,
SQLite defaults, boundary doctor behavior, all three verify phases, and an
independent coverage command.
